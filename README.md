# BimSAgent

## MCP4–MCP6: сравнение и унификация библиотеки семейств

Конвейер `MCP4 → JSON → MCP5 → JSON → MCP6 → JSON + HTML` реализован в фиксированных
папках `D:\BIM-S-MCP-4`, `D:\BIM-S-MCP-5`, `D:\BIM-S-MCP-6`. Результаты находятся
только в соответствующих папках `_Отчеты_...`. MCP5/MCP6 не читают RVT и не используют
RevitAPI. Отдельный add-in Revit 2024 использует `BIMS_FAMILY_BRIDGE`;
существующий мост MCP1 не меняется.

```powershell
dotnet run -- family pipeline --synthetic
dotnet run -- family pipeline --empty
dotnet run -- family pipeline --resume <pipelineId>
```

Эти команды доступны и в интерактивном BIM-S. Синтетический и пустой режимы
не перечисляют реальную библиотеку `D:\BIM-база ОВ`. Чтение библиотеки начинается
только при явно выбранном `family pipeline --library`. Добавление `--llm` включает
обычный совместимый API; без этого используются детерминированные рекомендации.

Длительные задания возвращают `runId`, сохраняют статусы, поддерживают отмену
и продолжение. BIM-S передаёт конкретные результаты между этапами, а не `latest`.
В LLM-контекст диалога попадают только компактные статусы и пути результатов.
Команды `mcp4-tools`–`mcp6-tools` и `mcp4-call`–`mcp6-call` доступны отдельно.

Основной отчёт — `report.html` MCP6. Высокая похожесть не отменяет несовместимость
коннекторов, хостинга или shared GUID; недоступные сведения отмечаются явно.
Текущий Revit-адаптер сохраняет ограничения наблюдаемости как `partial/missing`;
полнота извлечения и исполнение внутри живого Revit требуют отдельной проверки.

Визуальный слой `visual-v2` сравнивает изображения, цвета, рисунок поверхности,
контуры и состояния отображения. MCP4 получает адаптивный набор нативных снимков
Revit либо резервных изображений с ограниченной достоверностью; MCP5 использует
пиксельную метрику в общем проценте, MCP6 учитывает различия при рекомендации.
В HTML добавлены парные визуальные доказательства. Для дополнительной оценки
картинок API-моделью доступны `--llm` и `BIMS_FAMILY_LLM_VISION=1`.
Подробности: [визуальный анализ](D:/BIM-S-MCP-4/VISUAL-ANALYSIS.md).

Сборка, контракты, настройки LLM, инструменты и ограничения описаны в
[README MCP4](D:/BIM-S-MCP-4/README.md). Синтетические проверки:

```powershell
dotnet run --project D:\BIM-S-MCP-6\tests\BimS.Family.Tests.csproj
```

## MCP6: подбор оборудования по PDF-паспорту

```text
mcp6-call recommend-family-from-passport V001 "Имя паспорта.pdf"
```

Команда берёт опубликованный JSON MCP4 и ищет PDF по имени в `D:\BIM-база ОВ`.
MCP6 извлекает текст, пространственные таблицы, подписанные размеры, изображения
и схемы; сканы распознаёт Windows OCR. Сравнение всех семейств учитывает назначение,
параметры, размеры, коннекторы, фактическую геометрию и пиксельный внешний вид.
В отчёте — топ-3, рекомендуемый тип основы, цели изменений с цитатами,
совпадения, отличия и недостающие данные. Разные модели в паспорте не смешиваются.
Неоднозначные сведения, неподписанные размеры и ошибки OCR требуют проверки.

Отдельные `passport-result.json` и `passport-report.html` сохраняются в
`D:\BIM-S-MCP-6_Отчеты_Результат сравнения\runs\<runId>`; короткая команда публикует
новые `Vnnn.json` и `Vnnn.html` в той же фиксированной папке MCP6.
Данные паспорта, значения MCP4 и алгоритмические выводы разделены. Опциональная
мультимодальная интерпретация использует прежние настройки API и сохраняется
отдельно как гипотеза, не заменяя доказанные числовые цели.

Исходные PDF и семейства не изменяются. Проверки используют только синтетические
данные в папках результатов. [Подробная стратегия и ограничения](D:/BIM-S-MCP-6/PASSPORT-ANALYSIS.md).

## RAG: семейства, доказательства и локальные модели

RAG изолирован от истории диалога, памяти и MCP. C#/.NET 10 отвечает за извлечение,
индексы, поиск, группировку и вызов генератора. Модель ответа — `gpt-5.4-mini`;
embedding по умолчанию — `text-embedding-3-small`, 1536 измерений.
Ключ OpenAI читается из `OPENAI_API_KEY`, в конфигурационные файлы не записывается.

### Локальные сервисы

Установка выполняется отдельно от сборки C#. Модели, окружение и кеш находятся
в `D:\BIM-S_TestArtifacts\rag-models`, а не в Git:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/rag-models/Install-LocalModels.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools/rag-models/Start-Reranker.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools/rag-models/Start-Ocr.ps1
. ./tools/rag-models/Use-LocalModels.ps1
```

Последняя команда задаёт переменные только текущей PowerShell-сессии.
Сервисы слушают loopback; состояние: `http://127.0.0.1:8766/health` и
`http://127.0.0.1:8767/health`. Они запускаются в скрытых окнах, без автозапуска Windows.

Reranker — [BAAI/bge-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3),
зафиксирована ревизия `953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e`.
Пары вопрос/фрагмент оцениваются негeнеративным cross-encoder на CPU. Окна ограничиваются
его собственным tokenizer, без молчаливого truncation. Это дополнительные локальные
вычисления, а не дополнительные ответы LLM. INT8 можно отключить до запуска сервиса:
`$env:BIMS_RERANK_INT8='0'`. В `/health` показан фактический режим.

OCR — [EasyOCR](https://github.com/JaidedAI/EasyOCR) 1.7.2, русский и английский,
CPU. При обычном OCR изображения не отправляются в OpenAI. Результаты кешируются по SHA256 и версии
обработчика. Низкоуверенные надписи явно помечаются; OCR не доказывает правильность
размеров и не интерпретирует геометрию схем. Локальный OCR возвращает `vision_text` пустым.
Для описания формы запускайте отдельный vision-проход (OpenAI `gpt-5.4-mini`, существующий
`OPENAI_API_KEY`). Он отправляет изображения, сохраняет наблюдения по хэшу содержимого и версии
обработчика, отличает схему элемента от интерфейса и не заменяет OCR:

```powershell
dotnet 'D:\BIM-S_TestArtifacts\build\bin\BimSAgent\debug\BimSAgent.dll' rag index 'D:\BIM-база\Семейства Revit_Опалубка+Арматура.docx' --vision --family 'ФНК_Утолщение-приямок'
```

Без `--family` vision обрабатывает все поддерживаемые изображения документа; без `--vision`
новых vision-вызовов нет. Сохранённые описания используются повторно, включая обычную
переиндексацию. PNG/JPEG/WebP поддерживаются; другие форматы получают явный статус.
Описания входят в embeddings и отдельные structural-чанки с реальными `asset_id`, owner и
проверяемыми цитатами. Ответ по ним сопровождается оговоркой «По распознанному изображению»;
это не проверенные размеры или свойства модели Revit. Пустое описание не доказывает внешний вид.
Чтобы старый индекс получил эти данные, один раз выполните `rag index ... --vision`.
Текстовые embeddings пересчитываются только при изменении входа; полная повторная OCR-обработка не нужна.

### Команды

В `rag chat` вопросы о внешнем виде дополнительно получают связанные изображения найденного
семейства. Сначала используются сохранённые vision-чанки; если их нет, чат читает изображения
из исходного DOCX и распознаёт их через текущую модель OpenAI. Результаты и цитируемые чанки
сохраняются в `rag-data/visual-cache`, отдельно от истории и основной пары индексов.
Это дополнительные vision-вызовы при первом обращении к изображениям, с прежним безопасным
хранением API key. Повторные вопросы используют кэш по документу, изображению, семейству
и версии обработчика. Исходный DOCX должен быть доступен и соответствовать индексу.
Обычный retrieval/reranking выполняется на каждом сообщении; визуальные доказательства
добавляются по связи с семейством в пределах Top-K и бюджета контекста. Их similarity
не вычисляется, что явно помечается `linked_image:no_similarity` в диагностике.

`rag chat` — отдельный последовательный RAG-чат. Он не записывает `history.json`,
facts или основную память агента. История хранится как массив ходов, а цель,
уточнения, ограничения, термины, выбранные варианты и решения — отдельными полями
с дословным подтверждением пользователя и номером хода. По умолчанию файлы находятся
в `D:\BIM-S_TestArtifacts\rag-data\chats`; путь можно изменить через `BIMS_RAG_CHAT_DIRECTORY`.

```powershell
dotnet 'D:\BIM-S_TestArtifacts\build\bin\BimSAgent\debug\BimSAgent.dll' rag chat --new --strategy structural --improved --verbose
dotnet 'D:\BIM-S_TestArtifacts\build\bin\BimSAgent\debug\BimSAgent.dll' rag chat
dotnet 'D:\BIM-S_TestArtifacts\build\bin\BimSAgent\debug\BimSAgent.dll' rag chat --resume <id> --task 1
```

Без `--new` продолжается последний сохранённый чат. Внутри: `/state`, `/new`,
`/resume <id>`, `/task <id>`, `/task none`, `/exit`. Новый чат сохраняет предыдущий файл;
`/exit` возвращает управление основному интерактивному BIM-S, если чат запущен из него.
В этом случае привязывается активная задача основного агента; standalone CLI принимает `--task`.
Task state читается через существующий `ReadTask` на каждом ходе, переходы этапов не выполняются.

На ход выполняется один структурированный запрос подготовки поиска и обновлений состояния,
затем отдельные embedding/retrieval для каждого вопроса и один общий запрос ответа.
Подготовка учитывает последние 12 ходов (в пределах токен-бюджета), сохранённые факты и task state.
Она не выдаёт пользователю дополнительных ответов. Старые цитаты исключаются из истории,
фактический ответ проверяется только по текущим чанкам. Полная история остаётся на диске;
структурированное состояние ограничено 8000 токенами и не обрезается молча.
Явные пометки «Цель:», «Ограничение:», «Термин:», «Уточнение:», «Решение:» дополнительно
обрабатываются C#; использовать их необязательно. Повтор факта сохраняет его первоначальное
подтверждение. Для ссылочных вопросов C# добавляет известные семейства и определения
параметров в поисковый запрос, если модель не включила их; это не источники для цитирования.
`--baseline`, `--improved`, `--top-k`, `--strategy`, `--verbose` доступны в чате;
`--no-rag` и `--retrieval-only` остаются режимами `rag ask`.
Для semantic reranker перед запуском задайте `BIMS_RERANK_URL`/`BIMS_RERANK_MODEL` как выше.

Регрессии включают два сценария по 14 ходов с тестовыми API. Дополнительная живая проверка
14 и 12 сообщений (реальный OpenAI и индекс, `--baseline`, перезапуск посередине):
`powershell -NoProfile -ExecutionPolicy Bypass -File tests/Run-RagChatLive.ps1`.
Она читает существующие задачи 1/2, проверяет неизменность основных файлов и сохраняет
изолированные чаты и отчёты в `D:\BIM-S_TestArtifacts\rag-chat-live`.

```powershell
$app = 'D:\BIM-S_TestArtifacts\build\bin\BimSAgent\debug\BimSAgent.dll'
. ./tools/rag-models/Use-LocalModels.ps1
dotnet $app rag index 'D:\BIM-база\Семейства Revit_Опалубка+Арматура.docx'
dotnet $app rag status
dotnet $app rag ask 'Какие семейства подходят для площадки между лестничными маршами?' --strategy structural --verbose
dotnet $app rag ask 'Для чего используют IFC_Набор_Балка_№2?' --strategy structural --retrieval-only --json
dotnet $app rag ask '1. Какое семейство подходит для площадки? 2. Какое семейство подходит для армирования балки?' --strategy structural
dotnet $app rag ask 'Вопрос' --no-rag
dotnet $app rag compare 'Вопрос'
```

`--retrieval-only` не вызывает финальную LLM. Каждый вопрос списка получает собственный
embedding и retrieval; обычный `ask` делает один общий вызов генератора.
`--verbose` показывает выбранные фрагменты, исходный cosine, лексическую оценку,
режим и score reranker, владельца, exact match и причины исключения остальных кандидатов.
`--json` дополнительно сохраняет группировку по вопросам и реально переданный контекст;
embeddings в диагностику не включаются. `--verbose` и `--json` взаимоисключающие.
`--top-k` остался необязательным верхним пределом; количество результатов выбирается автоматически.

### Данные и поиск

`DocxDocumentExtractor` сохраняет XML-адреса блоков, строки/ячейки таблиц, объединения,
предполагаемые заголовки таблиц и image relationships. Первую строку таблицы следует
проверять как заголовок при нестандартном оформлении. Колонтитулы и сноски пока не извлекаются.
`FamilyCardBuilder` отделяет владельца от ссылок на другие семейства и регистрирует
конфликт вводного абзаца с заголовком. Это ограниченный детектор, не полная проверка
всех противоречий документа. Идентификаторы с № и суффиксами сравниваются целиком.
Карточки без надёжной идентификации остаются общими статьями.

Structural хранит родительские блоки до 2000 токенов, поисковые фрагменты до 650 токенов
и отдельные представления назначения. Сначала используются границы абзацев; overlap 100
применяется только при вынужденном разбиении слишком длинного атомарного блока.
Fixed сохраняет окна 600/100 и диапазоны принадлежности внутри окна.
`embedding_input` содержит подтверждённое назначение и локальный контекст;
шаблонная навигация исключается, исходный текст остаётся доступным.

Первый этап объединяет до 60 dense-кандидатов, до 40 лексических и точных владельцев.
Есть консервативная нормализация русских окончаний; это не полноценный морфологический словарь.
BM25-статистика вычисляется по полному индексу, каналы объединяются по рангам.
При заданном `BIMS_RERANK_URL` используется cross-encoder; иначе или при отказе сервиса
явно показывается `lexical_fallback`. Генеративного reranking нет.
Группировка даёт релевантным семействам по одному месту перед дополнительными фрагментами.
Дедупликация сохраняет различия чисел и отрицаний. Бюджет учитывает сериализованный
контекст с читаемым Unicode. Назначение передаётся вместе со ссылками на исходные блоки.

`BIMS_RERANK_MIN_SCORE` задаёт порог raw cross-encoder score (начальный -2.5).
Разрыв оценок дополняет порог. Это настраиваемая эвристика, не вероятность ответа;
значение нужно проверять на независимых вопросах. Для embedding сохранены
`BIMS_EMBEDDING_MODEL` и `BIMS_EMBEDDING_DIMENSIONS`; смена модели требует перестроения индекса.

Индексы `fixed.json` и `structural.json` находятся в `D:\BIM-S_TestArtifacts\rag-data`.
Схема v3 содержит блоки, карточки, assets, parent/child связи и manifest версий стадий.
После изменения extractor, card builder, chunking, embedding template или OCR-конфигурации
нужна полная логическая переиндексация. Команда та же `rag index`; вручную удалять JSON не нужно.
Неизменённый совместимый документ пропускается, кроме повторной обработки `processing_failed`
при подключённом OCR. Успешные OCR-результаты и неизменившиеся embeddings используются повторно.
У пары индексов проверяется общий build_id;
два файловых переименования не являются общей транзакцией. История поколений пока не ведётся.

### Проверки

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/Run-RagTests.ps1 -DocumentPath 'D:\BIM-база\Семейства Revit_Опалубка+Арматура.docx'
powershell -NoProfile -ExecutionPolicy Bypass -File tools/rag-models/Evaluate-Retrieval.ps1
```

Первая команда проверяет механику без OpenAI. Вторая использует реальный индекс,
OpenAI embeddings и локальный reranker, без генерации; отчёт находится в
`D:\BIM-S_TestArtifacts\retrieval-evaluation.json`. Контрольные вопросы и выдержки
из документа находятся в `tests/Rag/quality-cases.json`; небольшой набор не заменяет
экспертную оценку произвольных запросов. Наличие источников в JSON само по себе
не является автоматической проверкой обоснованности каждого утверждения LLM.

Для проверки сборки контекста на сохранённых реальных оценках без повторных API-вызовов:
```powershell
dotnet 'D:\BIM-S_TestArtifacts\build\Rag.Tests\bin\debug\Rag.Tests.dll' 'D:\BIM-база\Семейства Revit_Опалубка+Арматура.docx' 'D:\BIM-S_TestArtifacts\retrieval-evaluation.json'
```
Команда запускается из корня репозитория. Полные диапазоны происхождения текста остаются
в индексах; в prompt они не передаются, чтобы технические метаданные не вытесняли
описания других релевантных семейств из бюджета контекста.

MCP orchestration в `AskWithMcpAsync` использует один planner для полного плана,
последовательное выполнение MCP-шагов в C# и один финальный LLM-ответ.
Planner выбирает инструменты по описаниям/schema: текущее состояние требует
свежего snapshot, изменения во времени — snapshot и детерминированное сравнение.

| Задача | Последовательность |
|---|---|
| Текущее состояние модели | MCP1 `get-model` |
| Изменения модели | MCP1 `get-model` → MCP3, `mode: "3d"` |
| Текущее состояние документации | MCP2 `get-documentation` |
| Изменения документации | MCP2 `get-documentation` → MCP3, `mode: "2d"` |
| Изменения обоих разделов | MCP1 → MCP2 → MCP3, `mode: "both"` |

После шагов вызывается финальный LLM. Для свежего сравнения MCP3 получает
`version1: "previous", version2: "latest"`. Явно заданные сохранённые версии
сравниваются без обязательной новой выгрузки.

MCP3 разрешает aliases при запуске отдельно в каталогах модели и документации:
`latest` — максимальный числовой номер, `previous` — предыдущий существующий.
Пробелы в нумерации допустимы. Отсутствие предыдущего snapshot, повреждённый
или неполный выбранный JSON дают ошибку, а не сообщение «изменений нет».
При `both` с aliases MCP3 возвращает отдельные JSON/HTML для каждого раздела,
поскольку MCP1 и MCP2 нумеруют снимки независимо. Явная пара с `both` сохраняет
прежний общий отчёт. Файлы и правила их имён обрабатываются только серверами.

Ручные команды:

```text
mcp3-call compare-model-versions V003 V007
mcp3-call compare-model-versions previous latest
mcp3-call compare-model-versions {"version1":"previous","version2":"latest","mode":"3d"}
```

Без `mode` используется `both`. MCP1/MCP2 возвращают сам `snapshot` в
`StructuredContent`, MCP3 — `sections` с компактными `semanticChanges` по ElementId,
разрешённые версии и пути отчётов. Финальному LLM не нужно читать локальные файлы.
Большие snapshots могут исчерпать контекст модели; автоматического обрезания нет.

MCP3 формирует semantic changes детерминированно: один параметр определяется
ключом source/ownerElementId/parameterId, его значения выбираются в порядке
displayValue → convertedValue → rawValue. StructuredContent не содержит полных
oldState/newState, unchanged и технических differences; JSON/HTML отчёты сохраняют
полные данные. Если округлённые строки совпали при изменении rawValue, exactValues
содержит точные сохранённые значения. Изменения метаданных параметра обозначаются
отдельно. Финальный prompt требует перечислять только semanticChanges в формате
«название: old → new», группировать по ElementId и не придумывать причины.

Single-pass применяется только при `useMcp=true`: нет LLM-извлечения facts,
отдельной проверки/исправления ответа по invariants и классификации памяти.
Сами invariants остаются в prompt, история и Short-term сохраняются локально.
При `useMcp=false`, прямом `AskAsync`, `generate-prompt` и task workflow
обычная обработка остаётся включённой. CLI откладывает facts до решения planner.
Внешний вызывающий код может передать `prepareNonMcp` для обычной подготовки;
`LastResponseUsedMcp` позволяет не запускать постобработку памяти для MCP-ответа.
Подсчёт входных токенов использует отдельный counting endpoint, без генерации LLM.

Aliases означают последние файлы на момент сравнения. При параллельных экспортерах
они не гарантируют привязку к snapshot конкретного запроса. Текущая линия версий
на серверах — `Test_AI-Work`; идентичность модели и области 3D по JSON не доказана.

Команды управления контекстом:

- `strategy` — показать текущую стратегию и активную ветку.
- `strategy sliding-window` — последние 10 сообщений из `history.json` + новый запрос.
- `strategy sticky-facts` — факты из `facts.json` + последние 10 сообщений + новый запрос.
- `strategy branching` — полная исходная история активной ветки + её собственные сообщения.
- `checkpoint` — сохранить текущую историю как исходную точку новых веток.
- `branch create <name>` — создать независимую ветку из последнего checkpoint, без переключения.
- `branch switch <name>` — активировать ветку и стратегию Branching.

Например: `checkpoint`, `branch create option-a`, `branch create option-b`,
`branch switch option-a`; после диалога — `branch switch option-b`.
Вторая ветка не увидит сообщения первой. Новый checkpoint не меняет основание существующих веток.
Имена веток чувствительны к регистру. До первого переключения Branching использует полную историю.

Стратегия, checkpoint и ветки хранятся в `context-state.json`; факты — в `facts.json`
как JSON-объект ключ–значение. `history.json` остаётся полным журналом всех успешных обменов,
включая все ветки. Sliding Window и Sticky Facts используют последние 10 записей этого общего журнала.
Branching читает сообщения только своей ветки и её основания. Все файлы находятся в папке запуска.

В Sticky Facts каждое сообщение пользователя (включая задачу для `generate-prompt`)
сначала обрабатывается отдельным LLM-запросом. Извлечение сохраняет долгосрочные факты,
обновляет исправленные и удаляет явно отозванные; обычные вопросы и временные детали игнорируются.
Команды управления и синтетический тест контекста не извлекают факты.
Перед извлечением и перед основным ответом CLI отдельно спрашивает лимит токенов (16–32768)
и temperature (0–2). Эти параметры не сохраняются. Токены извлечения выводятся отдельно;
его служебные сообщения не добавляются в `history.json`. Ошибка извлечения сохраняет прежние факты
и останавливает текущий запрос. Успешное обновление фактов сохраняется даже при отмене основного ответа.

- `working-memory.json` — цель, входные данные, ограничения, промежуточные решения,

- `long-term-memory.json` — знания о Revit/API, Dynamo, C# и Python для будущих задач.

Каждый файл содержит массив записей с полями `id`, `scope`, `content`, `source`, `evidence`.
Новые UUID назначает C#. Локальные реплики short-term дополнительно имеют `role` user/assistant.

Сообщение пользователя записывается в Short-term перед основным API-запросом, ответ — после получения.

истории выбранной стратегии; старые записи Short-term без role по-прежнему доступны как память.
После каждого успешного ответа (также `generate-prompt`) Working/Long-term обновляется автоматически:
служебный запрос всегда использует `max_output_tokens: 500` и `temperature: 0.2`, без вопросов в CLI.
Параметры обычных запросов и отдельного извлечения Sticky Facts не меняются.
Уже полученный ответ остаётся в истории. Служебный ответ классификатора не добавляется в
`history.json`, его токены показываются отдельно. При запуске файлы загружаются без вызова LLM.
Память добавляется к контексту выбранной стратегии, поэтому учитывается счётчиком входных токенов.
`facts.json` и Sticky Facts продолжают работать отдельно, с прежней семантикой.

Краткосрочная и рабочая память имеют scope `main` либо `branch:<name>`; при переключении
веток чужие записи не передаются. Долгосрочные знания имеют scope `global` и доступны всем веткам.
Очистку устаревших сведений и актуальность задачи определяет LLM, автоматического удаления
при перезапуске нет. Содержимое памяти является контекстом, а не новой системной инструкцией.

Для общего знания API (`knowledgeKind: documented`) нужны URL официальной документации и дословная выдержка,
предоставленные пользователем в одном сообщении. C# проверяет наличие этих данных в диалоге
и допустимый домен источника. Это не независимая проверка содержимого сайта: приложение
не загружает документацию автоматически. LLM обязана сохранять только подтверждённые выдержкой
знания, указывать версии и не использовать собственные ответы как доказательство.
Для устойчивого факта проекта (`knowledgeKind: user-project`) достаточно `source: user` и точной
цитаты пользователя в evidence. Это утверждение о его проектах, а не о встроенном API Revit.
Например, задача сравнения моделей до/после Dynamo попадает в Working, а назначение пользовательского
параметра Блок_СМР — отдельной записью в Long-term, без утверждений об уникальности идентификатора.
Классификатор получает последний обмен и существующие записи Working/Long-term, возвращает
массив `changes` с любым числом записей для обоих слоёв. Изменения Short-term от LLM отклоняются.
Неподтверждённое знание отклоняется отдельно: корректная запись другого слоя сохраняется.
CLI показывает количество сохранённых, отклонённых и ожидающих выбора изменений.

Запись трёх файлов защищена журналом `memory-update-pending.json`: после прерывания
программа завершает сохранение при следующем запуске. JSON памяти исключены из Git.
История и существующие факты при добавлении этой функции не мигрируются и не удаляются.

Каждое изменение классификатора содержит `confidence`: `high`, `medium` или `low`.
`high` и `medium` сохраняются автоматически после проверки. `low` используется только
при реальной неоднозначности типа памяти: CLI показывает запись и спрашивает
«Не уверен, куда сохранить эту информацию. Выберите: short / working / long / skip:».
До выбора запись находится только в оперативной памяти. `skip`, конец ввода и выход
не сохраняют её. Выбор `long` требует соответствующего происхождения и цитаты:
документации для общего знания API либо утверждения пользователя для факта проекта.
Пользовательский выбор не вызывает дополнительного API-запроса. При неправильном вводе
или отсутствии доказательства для long можно повторить выбор. Обычные вопросы без
полезных сведений не должны порождать записи low и лишние вопросы.

Локальное управление записями (без API и ввода параметров генерации):

```text
memory <id> move from Short-term to Working Memory
memory <id> move from Working Memory to Long-term Memory
memory <id> delete from Long-term Memory
```

Разрешены любые направления между тремя типами. Можно использовать сокращения
`short`, `working`, `long`; регистр названий не важен. Источник проверяется по ID,
перенос в тот же тип ничего не меняет. ID, содержимое, источник и цитата сохраняются.
Ручное размещение отмечается `userPlaced: true`: перенос в long разрешён без документации
и сам по себе не означает проверки знания. Проверки источников для автоматических
изменений LLM остаются прежними. Scope при переносе в long становится global,
при переносе из long — текущим scope; между short и working сохраняется.
Команды могут управлять записью любой ветки по явно указанному ID. История и факты не меняются.

## Переключение LLM: OpenAI / Ollama

Провайдер выбирается при запуске через `BIMS_LLM_PROVIDER`. Значения: `openai` (по умолчанию, в том числе при пустой переменной) и `ollama`. Неизвестное значение останавливает запуск; автоматического отката на облако нет.

PowerShell, local:

```powershell
ollama pull qwen3:8b
$env:BIMS_LLM_PROVIDER = 'ollama'
dotnet run
```

Ollama должен быть запущен на `http://127.0.0.1:11434`. Приложение использует native `/api/chat`, модель `qwen3:8b`, без streaming и thinking. `OPENAI_API_KEY` для обычного диалога не требуется и в Ollama не отправляется. Планировщик агента, проверка инвариантов, факты, классификация/оптимизация памяти и LLM-операции задач также используют Ollama. Ошибка локальной генерации не вызывает OpenAI. История и память продолжают сохраняться локально. Настройки температуры и лимита ответа передаются локальной модели; точный облачный подсчёт токенов отключён.

PowerShell, cloud:

```powershell
$env:BIMS_LLM_PROVIDER = 'openai'
# OPENAI_API_KEY должен быть задан, как раньше.
dotnet run
```

При запуске выводится `LLM: Ollama / qwen3:8b` или `LLM: OpenAI / gpt-4.1-nano`. Облачная реализация Responses API и её модели для вспомогательных операций сохранены.

RAG намеренно остаётся на прежней реализации: его OpenAI embeddings, planner и генерация требуют облачного ключа даже при `BIMS_LLM_PROVIDER=ollama`. Команда `context-limit-test` проверяет лимит OpenAI и доступна только в cloud. MCP1–MCP6 и их серверы не изменены; переключается только LLM самого агента.
