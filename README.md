# BimSAgent

## RAG: первый этап

Команды RAG работают отдельно от диалога: не читают его историю, не обновляют память,
не запускают MCP и не используют профиль. Аргументный маршрут `rag` не создаёт
экземпляр `BimSAgent`. Те же команды доступны в интерактивной консоли.

Зависимости: `DocumentFormat.OpenXml` 3.5.1, `Microsoft.ML.Tokenizers` 2.0.0,
`Microsoft.ML.Tokenizers.Data.Cl100kBase` 2.0.0. Транзитивная зависимость
`Microsoft.Bcl.Memory` закреплена на исправленной версии 9.0.14.
OpenAI вызывается через `HttpClient`; ключ читается только из `OPENAI_API_KEY`.

Сборка и тесты с артефактами только в `D:\BIM-S_TestArtifacts`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/Run-RagTests.ps1 `
  -DocumentPath "D:\BIM-база\Семейства Revit_Опалубка+Арматура.docx"
```

Скрипт перенаправляет TEMP/TMP, NuGet-кеши и выход сборки в указанный каталог.
Тесты не вызывают OpenAI; `-DocumentPath` дополнительно проверяет извлечение и
разбиение реального документа. Без этого параметра проверяются синтетические DOCX.

После сборки команды можно вызывать без повторной сборки:

```powershell
$app = 'D:\BIM-S_TestArtifacts\build\bin\BimSAgent\debug\BimSAgent.dll'
dotnet $app rag index "D:\BIM-база\Семейства Revit_Опалубка+Арматура.docx"
dotnet $app rag status
dotnet $app rag compare "Какое семейство используется для лестничной площадки?"
dotnet $app rag ask "Какое семейство используется для лестничной площадки?" --strategy fixed
dotnet $app rag ask "Какое семейство используется для лестничной площадки?" --strategy structural
dotnet $app rag ask "Какое семейство используется для лестничной площадки?" --no-rag
```

`index`, `ask`, `compare` используют реальный OpenAI API; `status` не требует ключа.
`--no-rag` не требует индексов и не создаёт embedding вопроса.
`rag ask` также принимает последовательный список `"1. Первый вопрос 2. Второй вопрос 3. Третий вопрос"`
(в том числе с переводами строк). Список разбирается в C#: для каждого вопроса
выполняются отдельные embedding и retrieval с тем же top-K, затем один общий LLM-вызов.
Ответы имеют вид `⮕1. ...`, `⮕2. ...`. В `--no-rag` список также передаётся одним
LLM-вызовом, без поиска. Обычный вопрос без нумерации обрабатывается как прежде.
Разбор списка требует начала с `1.` и последовательных номеров с пробелом после точки;
при другой записи весь текст остаётся одним вопросом. `rag compare` не изменён.
`ask` и `compare` выбирают количество результатов автоматически. Прежний `--top-k N`
(1–100) остаётся необязательным верхним пределом. `--json` также сохранён.
Для `ask` доступен `--verbose`: перед ответом выводятся rank, chunk_id, section,
исходный similarity, rerank score, итоговый rank, exact match по семейству/терминам
и первые 400 символов каждого выбранного чанка. Для списка вопросов
диагностика сгруппирована по вопросам, rank начинается с 1 в каждой группе.
Показываются число проверенных чанков, размер расширенного набора кандидатов и число
выбранных для LLM чанков; перечисляются именно выбранные чанки.
Флаг не меняет поиск или prompt и не добавляет API-вызовов; без него вывод прежний.
`--verbose` и `--json` не совмещаются. В NO-RAG выводится сообщение об отсутствии поиска.
Диагностический JSON содержит ответ, source/section/chunk_id/strategy и similarity score,
без векторов. Это найденные источники, а не проверенные цитаты.

Обычный `compare` выводит только:

```text
Фиксированное разбиение:
<короткий ответ>

Структурное разбиение:
<короткий ответ>
```

Оба режима используют `gpt-4.1-nano`, temperature=0, max_output_tokens=600,
одинаковый вопрос, правила отбора и бюджет контекста. Вопрос в сравнении векторизуется один раз.
NO-RAG использует ту же модель и настройки, но разрешает ответ из знаний модели без
документального контекста: это baseline, а не подтверждённое описание корпоративных семейств.

DOCX читается через Open XML DOM с сохранением порядка абзацев и строк таблиц.
Для устойчивости к отсутствующим изображениям загружаются только XML документа и
стилей, без разрешения media relationships. Исходный файл не изменяется. Учитываются
уровни заголовков, наследование стилей и русские имена. Названия семейств извлекаются
консервативно из заголовков, явных полей и подписанной колонки таблицы;
произвольные имена параметров с подчёркиванием не считаются семействами.
Исправления читаются без удалённого текста. Изображения/OCR, колонтитулы и сноски
не индексируются; текст на иллюстрациях не участвует в ответах.

Fixed: окна до 600 токенов с overlap около 100. Structural: собирается целое описание
семейства, включая подразделы, абзацы, таблицы и инструкции. Блок до 2000 токенов
остаётся целым; более длинный делится окнами с overlap около 100 токенов.
Дочерние чанки имеют общий `parent_block_id`, а раздел и семейство сохраняются в метаданных.
Границы другого семейства не пересекаются. Без распознанного семейства используются
разделы документа. Токены считаются локально через cl100k_base.
Для обеих стратегий embedding-вход одинаково составляется из раздела, извлечённых
имён семейств и текста; точный вход сохраняется в индексе.

По умолчанию индексация вызывает `text-embedding-3-small` (1536 измерений), пакетами по 16.
Модель задаётся переменной `BIMS_EMBEDDING_MODEL` (`text-embedding-3-small` или
`text-embedding-3-large`); размерность — `BIMS_EMBEDDING_DIMENSIONS` (необязательно,
по умолчанию 1536 для small и 3072 для large). Автоматического переключения нет.
При изменении модели/размерности нужна переиндексация: кеш другой модели не используется,
а поиск при несовпадении конфигурации завершается до API-вызова с понятной ошибкой.
Два самостоятельных JSON-индекса находятся в `D:\BIM-S_TestArtifacts\rag-data`:
`fixed.json` и `structural.json`. Каждая запись содержит `source`, `title`, `file`,
`section`, детерминированный `chunk_id`, `strategy`, `text`, `embedding_input`,
`embedding`, `embedding_model`, `token_count`, `family_names`, `block_ordinals`.
Метаданные индекса содержат версию схемы, хеш документа, параметры chunking,
размерность, время и общий идентификатор операции индексации.

**После изменения structural-размера на 2000 требуется повторная индексация.**
Формат остаётся v2, но проверяется сохранённый размер: поиск по structural-индексу
с прежними 1200 токенами сообщает о необходимости выполнить `rag index`.
Команда пересобирает пару даже при неизменённом DOCX, переиспользуя совместимые
embeddings, включая fixed. Прежний формат v1 также требует пересборки.
Reranking сам по себе переиндексации не требует. Вручную удалять файлы не надо:

```powershell
dotnet "D:\BIM-S_TestArtifacts\build\bin\BimSAgent\debug\BimSAgent.dll" rag index "D:\BIM-база\Семейства Revit_Опалубка+Арматура.docx"
```

Повторите `rag index` после изменения DOCX. Совместимый неизменённый документ пропускается без
API-вызовов; подходящие сохранённые embeddings переиспользуются при обновлении.
В этом этапе хранится один документ: индексация другого файла заменяет оба индекса.
Повреждённый индекс можно восстановить этой же командой.
Оба файла готовятся до публикации; сбой embeddings не затрагивает прежние индексы.
Замена двух файлов не является общей транзакцией: если процесс прерван между заменами,
`compare` обнаружит несовпадение идентификаторов и попросит повторить индексацию.
История поколений не ведётся; после обновления прежние chunk_id могут отсутствовать.

Первый этап retrieval детерминированно сочетает cosine и точные совпадения. Внутренний набор —
до 40 лучших по cosine (или больше при явном лимите), до 20 по покрытию терминов и
все exact-family совпадения из полного индекса. Термины сравниваются
без учёта регистра и ё/е, по целым словам, с исключением стоп-слов и весами частотности.
Морфологического анализа пока нет. Косинус в диагностике остаётся исходным.

Второй этап — `IReranker` / `Bm25Reranker`, локальный C# без сторонних сервисов и LLM.
Весь расширенный набор поступает в reranker до финальных отсечек. Каждый кандидат
оценивается относительно исходного вопроса: BM25 по тексту целого чанка и лучшему
окну из 128 содержательных слов, шаг 96. IDF рассчитывается по набору кандидатов;
k1=1.2, b=0.75, как в [описании BM25](https://lucene.apache.org/core/9_12_3/core/org/apache/lucene/search/similarities/BM25Similarity.html).
Лексическая оценка L = 0.4 * BM25 целого текста + 0.6 * BM25 лучшего окна.
Rerank score = 0.4 * cosine + 0.6 * L/(1+L); для вопроса без содержательных слов
используется исходный cosine. Exact-family добавляет 2, прямое упоминание в тексте —
ещё 0.25. Это эвристическая шкала, а не вероятность и не чистый BM25 score.
Механизм лексический: он не является нейросетевым cross-encoder и не понимает
синонимы без совпадений слов. Его можно заменить через `IReranker`.

После reranking удаляются одинаковые и близкие тексты (Jaccard трёхсловных шинглов >= 0.88),
но не объединяются разные семейства, числовые значения и отрицания. Финальные отсечки
применяются к rerank score, не к прежнему cosine: минимум 0.15, отставание от лидера
не более 0.18, крупнейший разрыв соседних rerank score более 0.08 (без exact-family).
Exact-family защищён от отсечек. Автоматический максимум — 12,
фактическое количество может быть меньше или нулевым. Это начальные эвристики,
не откалиброванная оценка достоверности; качество проверяется на реальных вопросах.
Генератор получает только отобранный контекст, до 6000
токенов с резервом на метаданные. При пустом контексте возвращается «не знаю» без
LLM-вызова; при непустом генератору предписано отвечать только по фрагментам и
признавать недостаток сведений. Семантическая проверка этой инструкции пока отсутствует.
Документ не подтверждает наличие и изменения экземпляров в конкретной модели Revit.

Код разделён на извлечение/разбиение, индексацию/хранилище, embeddings, retrieval,
генерацию и CLI. `IEmbeddingClient`, `IIndexStore`, `IRetriever`, `IRagAnswerGenerator`
подменяются в тестах; `RagAnswer` сохраняет источники и scores для дальнейшего развития.
Следующий этап: query rewrite, LLM reranking, калибровка порогов, цитаты/grounding, версии,
оценочный набор и подключение к MCP-планировщику. Они сейчас не реализованы.

MCP orchestration в `AskWithMcpAsync` использует один planner для полного плана,
последовательное выполнение MCP-шагов в C# и один финальный LLM-ответ.
Planner выбирает инструменты по описаниям/schema: текущее состояние требует
свежего snapshot, изменения во времени — snapshot и детерминированное сравнение.

| Задача | Последовательность |
|---|---|
| Текущее состояние модели | MCP1 `get-model` |
| Изменения модели | MCP1 `get-model` → MCP3, `mode: "3d"` |
| Текущее состояние документации | MCP2 `get-documentation` |
| Изменения документации | MCP2 `get-documentation` → MCP3, `mode: "2d"` |
| Изменения обоих разделов | MCP1 → MCP2 → MCP3, `mode: "both"` |

После шагов вызывается финальный LLM. Для свежего сравнения MCP3 получает
`version1: "previous", version2: "latest"`. Явно заданные сохранённые версии
сравниваются без обязательной новой выгрузки.

MCP3 разрешает aliases при запуске отдельно в каталогах модели и документации:
`latest` — максимальный числовой номер, `previous` — предыдущий существующий.
Пробелы в нумерации допустимы. Отсутствие предыдущего snapshot, повреждённый
или неполный выбранный JSON дают ошибку, а не сообщение «изменений нет».
При `both` с aliases MCP3 возвращает отдельные JSON/HTML для каждого раздела,
поскольку MCP1 и MCP2 нумеруют снимки независимо. Явная пара с `both` сохраняет
прежний общий отчёт. Файлы и правила их имён обрабатываются только серверами.

Ручные команды:

```text
mcp3-call compare-model-versions V003 V007
mcp3-call compare-model-versions previous latest
mcp3-call compare-model-versions {"version1":"previous","version2":"latest","mode":"3d"}
```

Без `mode` используется `both`. MCP1/MCP2 возвращают сам `snapshot` в
`StructuredContent`, MCP3 — `sections` с компактными `semanticChanges` по ElementId,
разрешённые версии и пути отчётов. Финальному LLM не нужно читать локальные файлы.
Большие snapshots могут исчерпать контекст модели; автоматического обрезания нет.

MCP3 формирует semantic changes детерминированно: один параметр определяется
ключом source/ownerElementId/parameterId, его значения выбираются в порядке
displayValue → convertedValue → rawValue. StructuredContent не содержит полных
oldState/newState, unchanged и технических differences; JSON/HTML отчёты сохраняют
полные данные. Если округлённые строки совпали при изменении rawValue, exactValues
содержит точные сохранённые значения. Изменения метаданных параметра обозначаются
отдельно. Финальный prompt требует перечислять только semanticChanges в формате
«название: old → new», группировать по ElementId и не придумывать причины.

Single-pass применяется только при `useMcp=true`: нет LLM-извлечения facts,
отдельной проверки/исправления ответа по invariants и классификации памяти.
Сами invariants остаются в prompt, история и Short-term сохраняются локально.
При `useMcp=false`, прямом `AskAsync`, `generate-prompt` и task workflow
обычная обработка остаётся включённой. CLI откладывает facts до решения planner.
Внешний вызывающий код может передать `prepareNonMcp` для обычной подготовки;
`LastResponseUsedMcp` позволяет не запускать постобработку памяти для MCP-ответа.
Подсчёт входных токенов использует отдельный counting endpoint, без генерации LLM.

Aliases означают последние файлы на момент сравнения. При параллельных экспортерах
они не гарантируют привязку к snapshot конкретного запроса. Текущая линия версий
на серверах — `Test_AI-Work`; идентичность модели и области 3D по JSON не доказана.

Тесты orchestration подменяют HTTP/MCP и проверяют порядок вызовов и сохранение
обычного режима. Тесты MCP3 используют синтетические снимки, проверяют aliases,
реальную schema через `tools/list` и вызовы через stdio; реальные выгрузки не меняют.

Задачи хранятся в `C:\Users\Anastasia\OneDrive\Desktop\BimSAgent\tasks`.
`task create Проверка модели` локально создаёт следующий `task-N.json` с полями
`id`, `name`, `state: "PLANNING"`, `currentStep: ""`, `expectedAction: ""`.
Номер определяется по максимальному существующему номеру файла; файлы не перезаписываются.
Создание не активирует задачу. `task open 1` загружает задачу и активирует её в текущем сеансе.
Перед каждым обычным запросом и `generate-prompt` JSON активной задачи перечитывается,
его состояние добавляется в контекст перед новым запросом пользователя и учитывается
счётчиком входных токенов. Служебные запросы памяти и тест контекста не меняются.
После перезапуска задачу нужно открыть командой. Обычный запрос при открытой незавершённой
задаче запускает цикл PLANNING → EXECUTION → VALIDATION → DONE. План согласуется меню
из трёх вариантов: принять, перегенерировать, внести правки. Каждый шаг выполнения
подтверждается отдельно. Замечания при проверке возвращают задачу в EXECUTION:
в план добавляется шаг исправлений, после его подтверждения итог проверяется повторно.
Переходы выполняет C# только после выбора пользователя. В том же JSON сохраняются
`plan`, `state`, `currentStep`, `expectedAction`, индекс шага `stepIndex` и результаты
с замечаниями `results`, чтобы итоговая проверка не зависела от окна истории.
Существующий файл без `plan` дополняется при `task open`. Параметры генерации
запрашиваются перед каждым ответом; `generate-prompt` не запускает переходы задачи.

`task pause` сохраняет состояние активной задачи в том же JSON и отключает её от
текущего диалога. Команда доступна также в меню подтверждения и при вводе замечаний.
`task open <id>` показывает имя, этап, текущий шаг и ожидаемое действие и продолжает
работу с сохранённого состояния. Если ответ уже получен, он показывается локально
с меню подтверждения без повторной генерации. Поля `awaitingChoice` и `pendingInput`
сохраняют точку продолжения и запрос для ещё не выполненного шага.

Для активной задачи Working Memory и локальный диалог имеют scope `task:<id>`.
Основной запрос получает только диалог этой задачи из Short-term Memory, её Working
Memory, глобальную Long-term Memory и состояние задачи. Общая history и ветки
в контекст задачи не добавляются. История продолжает сохраняться в history.json.
Классификатор памяти получает только новый успешный обмен пользователь/ассистент,
без массивов существующей памяти и состояния задачи. C# локально сохраняет новые
факты и сопоставляет точные совпадения content внутри соответствующего слоя и scope,
сохраняя существующий id. Более конкретные сведения сохраняются отдельно.
Старые записи main/branch не перепривязываются к задачам автоматически: в них нет
достоверной информации о принадлежности конкретной задаче.

Пользовательские профили находятся в `C:\Users\Anastasia\OneDrive\Desktop\BimSAgent\profiles`.

- `profile create <name>` — последовательно ввести Style, Constraints и Context;
  сохранить JSON с полями `style`, `constraints`, `context` без API-запроса.
- `profile use <name>` — включить профиль для обычных ответов и `generate-prompt`.
- `profile show` — вывести имя и все поля активного профиля.
- `profile list` — показать существующие профили.
- `profile skip` — отключить профиль.

Создание не активирует профиль и не перезаписывает существующий файл. Выбор сохраняется
в `profiles/.active-profile.json` и восстанавливается при запуске. `/exit` или конец ввода
во время опроса отменяет создание и завершает программу. Допускаются пустые поля.
Имена: до 64 букв, цифр, дефисов или подчёркиваний, без системных имён Windows.
Профиль добавляется к инструкциям текущего обычного запроса; в историю и память отдельно
не записывается. Служебные вызовы классификации памяти, Sticky Facts и тест переполнения
не получают профиль. Общий счётчик `usage.input_tokens` учитывает добавленные инструкции.

Working/Long-term формируются атомарно: один факт, параметр, термин, решение или требование —
одна запись с собственным ID. Общие темы, заголовки и пересказы не сохраняются классификатором.
`content` и `description` относятся к одному факту и содержат точные названия сущностей
и необходимую область применимости. Перечисления разбиваются на отдельные объекты `changes`;
C# назначает каждой новой записи UUID. Существующие записи автоматически не переразбиваются.
Уточнение существующей темы не считается дубликатом: классификатор обновляет прежний ID
более конкретным фактом либо оставляет его первому факту при разбиении и создаёт остальные
с новыми ID. Совместимые ранее известные детали и точные названия должны сохраняться.
Пропускаются только сведения, уже представленные с такой же или большей точностью.

Существующие Working/Long-term записи однократно разобраны на факты из их content.
Исходные файлы сохранены в `.memory-backups/20260912-144224/`. Первый факт каждой исходной
записи сохраняет её ID; дополнительные получают новые UUID. Метаданные наследуются.
Неуточнённые цели не дополнялись вымышленными данными, возможные причины оставлены гипотезами.

Во всех трёх файлах памяти сразу после `id` записывается `description` — короткое описание
на русском языке: один конкретный факт без вводных фраз, пояснений и пересказа контекста.
Технические названия сохраняются точно, без обобщений, переименования и обрезания.
Для Working/Long-term его формирует существующий классификатор без
дополнительного API-запроса. Для локальных реплик Short-term описание создаёт C#.
Старые записи без description получают локальное описание из содержимого при загрузке;
ID и остальные поля сохраняются. Если классификатор не вернул описание, применяется тот же
локальный резервный вариант. Кириллица в файлах памяти сохраняется обычными UTF-8 символами.
Локальный вариант берёт первый законченный фрагмент исходного текста без добавления
«Сообщение пользователя», «Ответ агента» или «Сведения» и без ограничения в 120 символов,
которое могло обрезать техническое название. Существующие непустые description автоматически не переписываются.
Переносы между слоями сохраняют description вместе с записью.

Актуальное правило Working/Long-term: `high` и `medium` сохраняются в слой, выбранный LLM.
`source`, `evidence` и `knowledgeKind` являются метаданными, а не условиями допуска:
C# не проверяет домен документации и дословное совпадение цитат, в том числе при загрузке.
`low` ждёт выбора `short / working / long / skip` без записи на диск.
Технические ошибки (неизвестный ID, неверные поля, пустой content, чужая ветка) выводятся
с номером записи и причиной; корректные соседние записи обрабатываются независимо.
Ни уверенность модели, ни успешное сохранение сами по себе не подтверждают истинность знания.

Консольный AI-помощник по Autodesk Revit, BIM, Revit API, C#-плагинам и Dynamo.
Требуется .NET 10 SDK. Зависимости перечислены в `BimSAgent.csproj`.

Из родительской папки:

```powershell
dotnet build .\BimSAgent\BimSAgent.csproj
dotnet run --project .\BimSAgent\BimSAgent.csproj
```

Перед запросом задайте `OPENAI_API_KEY` в окружении процесса через безопасный
механизм вашей среды. Приложение не запрашивает ключ в CLI, не сохраняет его
в файлы и не выводит в журнал. Сборка не требует ключа и не обращается к API.

Модель — `gpt-4.1-nano` (зафиксирована в коде, `OPENAI_MODEL` не используется).
Введите запрос одной строкой; `/exit`, Ctrl+C или конец ввода завершают работу.
Команда `generate-prompt` запрашивает задачу, затем лимит токенов ответа (целое число
от 16 до 32768) и создаёт один технический
prompt для её дальнейшего решения, без самого решения. Инструкции этого режима требуют
использовать только реальные возможности Autodesk Revit 2024 и Revit API 2024,
не выдумывать API и явно указывать отсутствие прямого способа, если его нет.
Задача с пометкой команды и созданный prompt сохраняются в обычной истории.
После prompt выводится стандартная статистика токенов; счётчик текущего запроса
включает пометку команды. Пустая задача отменяет команду без вызова API.
Полная история загружается из history.json в текущей рабочей папке при запуске.
Состав контекста определяется выбранной стратегией (по умолчанию Sliding Window).
После успешного ответа запрос и ответ добавляются в history.json без сжатия.
Существующие summary-файлы и memory-pending.json не читаются и не изменяются.
Для продолжения диалога запускайте программу из той же папки.
Если файла нет, начинается новый диалог; файл создаётся после первого успешного ответа.
Повреждённая или недоступная история вызывает сообщение об ошибке и не перезаписывается.
При ошибке API новый обмен не сохраняется. Очень длинная история
может превысить контекстное окно модели: автоматического усечения запроса нет.
Агент консультирует и генерирует текст, но не подключается к Revit.

Используется [OpenAI Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create),
с инструкциями роли в `instructions` и запросом в `input`.

После ответа выводятся токены текущего сообщения и предыдущей истории
(фактически переданного контекста выбранной стратегии, включая facts при Sticky Facts)
(отдельные вызовы `/v1/responses/input_tokens`, включая служебное оформление сообщений,
без инструкций роли). Для пустой истории выводится 0. Эти независимые счётчики
не следует складывать: каждый включает оформление отдельного входа.
Общий фактический вход с инструкциями и размер ответа берутся из `usage.input_tokens`
и `usage.output_tokens`. Если счётчик недоступен, выводится «недоступно», без оценки LLM.

Команда `context-limit-test` создаёт синтетический контекст и корректирует его размер
по счётчику API до ровно 1 050 000 входных токенов, включая инструкции и оформление.
Затем отправляет его с `truncation: disabled` и выводит ошибку `context_length_exceeded`.
Другие ошибки (например, HTTP 429) не считаются подтверждением переполнения.
Если подтвердить размер через API не удалось, генерация не запускается.
Тест не использует и не изменяет историю диалога. Команда выполняет реальные API-запросы
только при ручном вводе; сборка её не запускает.

Справка: [подсчёт входных токенов](https://developers.openai.com/api/reference/typescript/resources/responses/subresources/input_tokens),
[лимиты GPT-4.1 nano](https://developers.openai.com/api/docs/models/gpt-4.1-nano).

Команды управления контекстом:

- `strategy` — показать текущую стратегию и активную ветку.
- `strategy sliding-window` — последние 10 сообщений из `history.json` + новый запрос.
- `strategy sticky-facts` — факты из `facts.json` + последние 10 сообщений + новый запрос.
- `strategy branching` — полная исходная история активной ветки + её собственные сообщения.
- `checkpoint` — сохранить текущую историю как исходную точку новых веток.
- `branch create <name>` — создать независимую ветку из последнего checkpoint, без переключения.
- `branch switch <name>` — активировать ветку и стратегию Branching.

Например: `checkpoint`, `branch create option-a`, `branch create option-b`,
`branch switch option-a`; после диалога — `branch switch option-b`.
Вторая ветка не увидит сообщения первой. Новый checkpoint не меняет основание существующих веток.
Имена веток чувствительны к регистру. До первого переключения Branching использует полную историю.

Стратегия, checkpoint и ветки хранятся в `context-state.json`; факты — в `facts.json`
как JSON-объект ключ–значение. `history.json` остаётся полным журналом всех успешных обменов,
включая все ветки. Sliding Window и Sticky Facts используют последние 10 записей этого общего журнала.
Branching читает сообщения только своей ветки и её основания. Все файлы находятся в папке запуска.

В Sticky Facts каждое сообщение пользователя (включая задачу для `generate-prompt`)
сначала обрабатывается отдельным LLM-запросом. Извлечение сохраняет долгосрочные факты,
обновляет исправленные и удаляет явно отозванные; обычные вопросы и временные детали игнорируются.
Команды управления и синтетический тест контекста не извлекают факты.
Перед извлечением и перед основным ответом CLI отдельно спрашивает лимит токенов (16–32768)
и temperature (0–2). Эти параметры не сохраняются. Токены извлечения выводятся отдельно;
его служебные сообщения не добавляются в `history.json`. Ошибка извлечения сохраняет прежние факты
и останавливает текущий запрос. Успешное обновление фактов сохраняется даже при отмене основного ответа.

Дополнительная память хранится в трёх отдельных файлах:

- `short-term-memory.json` — реплики текущего диалога, сохраняемые локально C# без отдельного API-запроса.
- `working-memory.json` — цель, входные данные, ограничения, промежуточные решения,
  выбранный способ и результат текущей задачи; обычный разговор сюда не переносится.
- `long-term-memory.json` — знания о Revit/API, Dynamo, C# и Python для будущих задач.

Каждый файл содержит массив записей с полями `id`, `scope`, `content`, `source`, `evidence`.
Новые UUID назначает C#. Локальные реплики short-term дополнительно имеют `role` user/assistant.
LLM выбирает содержание только Working и Long-term. При обновлении или переносе
записи UUID сохраняется. LLM возвращает JSON-план `changes` с операциями `upsert` и `delete`;
C# проверяет весь план до записи, отклоняет неизвестные ID и изменения чужой ветки.
Для переноса используется прежний ID и новый тип памяти. Перенос в long-term требует источника.

Сообщение пользователя записывается в Short-term перед основным API-запросом, ответ — после получения.
Существующие записи и ID не перезаписываются. Локальные реплики не дублируются в контексте поверх
истории выбранной стратегии; старые записи Short-term без role по-прежнему доступны как память.
После каждого успешного ответа (также `generate-prompt`) Working/Long-term обновляется автоматически:
служебный запрос всегда использует `max_output_tokens: 500` и `temperature: 0.2`, без вопросов в CLI.
Параметры обычных запросов и отдельного извлечения Sticky Facts не меняются.
Уже полученный ответ остаётся в истории. Служебный ответ классификатора не добавляется в
`history.json`, его токены показываются отдельно. При запуске файлы загружаются без вызова LLM.
Память добавляется к контексту выбранной стратегии, поэтому учитывается счётчиком входных токенов.
`facts.json` и Sticky Facts продолжают работать отдельно, с прежней семантикой.

Краткосрочная и рабочая память имеют scope `main` либо `branch:<name>`; при переключении
веток чужие записи не передаются. Долгосрочные знания имеют scope `global` и доступны всем веткам.
Очистку устаревших сведений и актуальность задачи определяет LLM, автоматического удаления
при перезапуске нет. Содержимое памяти является контекстом, а не новой системной инструкцией.

Для общего знания API (`knowledgeKind: documented`) нужны URL официальной документации и дословная выдержка,
предоставленные пользователем в одном сообщении. C# проверяет наличие этих данных в диалоге
и допустимый домен источника. Это не независимая проверка содержимого сайта: приложение
не загружает документацию автоматически. LLM обязана сохранять только подтверждённые выдержкой
знания, указывать версии и не использовать собственные ответы как доказательство.
Для устойчивого факта проекта (`knowledgeKind: user-project`) достаточно `source: user` и точной
цитаты пользователя в evidence. Это утверждение о его проектах, а не о встроенном API Revit.
Например, задача сравнения моделей до/после Dynamo попадает в Working, а назначение пользовательского
параметра Блок_СМР — отдельной записью в Long-term, без утверждений об уникальности идентификатора.
Классификатор получает последний обмен и существующие записи Working/Long-term, возвращает
массив `changes` с любым числом записей для обоих слоёв. Изменения Short-term от LLM отклоняются.
Неподтверждённое знание отклоняется отдельно: корректная запись другого слоя сохраняется.
CLI показывает количество сохранённых, отклонённых и ожидающих выбора изменений.

Запись трёх файлов защищена журналом `memory-update-pending.json`: после прерывания
программа завершает сохранение при следующем запуске. JSON памяти исключены из Git.
История и существующие факты при добавлении этой функции не мигрируются и не удаляются.

Каждое изменение классификатора содержит `confidence`: `high`, `medium` или `low`.
`high` и `medium` сохраняются автоматически после проверки. `low` используется только
при реальной неоднозначности типа памяти: CLI показывает запись и спрашивает
«Не уверен, куда сохранить эту информацию. Выберите: short / working / long / skip:».
До выбора запись находится только в оперативной памяти. `skip`, конец ввода и выход
не сохраняют её. Выбор `long` требует соответствующего происхождения и цитаты:
документации для общего знания API либо утверждения пользователя для факта проекта.
Пользовательский выбор не вызывает дополнительного API-запроса. При неправильном вводе
или отсутствии доказательства для long можно повторить выбор. Обычные вопросы без
полезных сведений не должны порождать записи low и лишние вопросы.

Локальное управление записями (без API и ввода параметров генерации):

```text
memory <id> move from Short-term to Working Memory
memory <id> move from Working Memory to Long-term Memory
memory <id> delete from Long-term Memory
```

Разрешены любые направления между тремя типами. Можно использовать сокращения
`short`, `working`, `long`; регистр названий не важен. Источник проверяется по ID,
перенос в тот же тип ничего не меняет. ID, содержимое, источник и цитата сохраняются.
Ручное размещение отмечается `userPlaced: true`: перенос в long разрешён без документации
и сам по себе не означает проверки знания. Проверки источников для автоматических
изменений LLM остаются прежними. Scope при переносе в long становится global,
при переносе из long — текущим scope; между short и working сохраняется.
Команды могут управлять записью любой ветки по явно указанному ID. История и факты не меняются.
